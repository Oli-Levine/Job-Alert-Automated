# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A single Google Apps Script file (`Code.gs`, currently v24) that automates job-alert triage for BCL Legal. It is bound to a Google Sheet, reads LinkedIn/Indeed job-alert emails from Gmail, classifies each listing with the Claude API, downloads each lead's full job description, and writes results into a `New Leads` tab that is imported directly into the company CRM. There is no package manager, build step, linter, or test runner — this is plain Apps Script (V8 runtime) deployed by pasting the file's contents into the Apps Script editor (which names the file `Code.gs` by default) bound to the Google Sheet.

## Working with this codebase

- There is only one source file, `Code.gs`. The filename is stable across versions — do NOT rename it per version (an earlier convention renamed the file itself, e.g. `V17` → `V18`; that's retired, since it fought git's own history instead of using it). Version identity lives in exactly two places: the header comment's version number (bump it on a meaningful change) and git history/log (use `git log`, `git diff`, or `git show <commit>:Code.gs` to inspect or recover a prior version).
- The file's top-of-file comment block is a running changelog ("CHANGES FROM v18", "CHANGES FROM v17 (carried forward)", ...), keeping the two most recent entries and dropping older ones. When making a meaningful change, bump the version number in the header comment and add a new entry describing what changed and why — this is the project's in-file changelog; git history is the source of truth for anything older than what it keeps.
- There's no automated test suite. Verification happens via the diagnostic/dry-run functions defined in the file itself, run manually from the Apps Script editor against the live Gmail/Sheet data:
  - `testParseLatestEmail()` — dry run: parses the latest matching email and logs what Claude would classify (the Staff ID a routed job would get, and the region a filtered job would use if unfiltered), without writing anything. It does not apply the blocklists, Unfilter Company, Company Regions or the Bournemouth/Poole/Christchurch code check.
  - `debugIndeedLinks()` — logs raw vs. detected Indeed job links, for diagnosing link-extraction regressions.
  - `debugListSheetNames()` — logs actual sheet tab names vs. expected working tab names (catches naming/whitespace mismatches).
  - `listAllTriggers()` — lists what time-based triggers are currently installed on this sheet's script.
  - `runDailySend()` — can be run by hand to send the workbook email immediately.
  - `applyListsNow()` — re-applies the override lists to rows already in the sheet straight away (see "List changes" below), without fetching new emails.
  - There are no separate description tools: `processJobAlerts()` fills descriptions for the leads it adds, in the same run, and logs a one-line summary (`Job descriptions: N filled, N sponsored Indeed (skipped), N FETCH FAILED`) plus each Apify run's status, result count and result field names — check the execution log first when descriptions fail.
- Sponsored Indeed jobs (`pagead/clk` ad links, no `jk`) deliberately get no description (`DESCRIPTION_SPONSORED`). Tried and ruled out before v24 (details in git history on branch `claude/sponsored-indeed-test`): reading the ad redirect from Apps Script (Indeed 403s the first hop); giving ad links to `misceres~indeed-scraper` (fails the whole run — so never mix them into an Indeed run); browser actors on Apify (`apify~web-scraper` etc.) were refused over the API with "requires full access" (an Apify account-permission approval issue, never resolved). Untested ideas if they're revisited: find the same job on LinkedIn (free guest search) and accept only an exact company + title match, or an Indeed search via the scraper (found 1 of 3 earlier).
- `resetAllJobData()` is a destructive utility for the live spreadsheet — don't suggest running it casually. `migrateConsultantTabsToNewLeads()` is a one-off migration (see below) meant to be run once, not on a schedule.
- Because the sheet feeds a CRM import, the New Leads column layout is effectively an external contract — adding, removing or reordering its columns affects the import, so treat it as a user decision, not a refactor.

## Architecture

**Entry point:** `processJobAlerts()` is the main daily job. It:
1. Loads reference/override sheets (`loadOverrideLists()`): `Company Blocklist`, `Job Title Blocklist` (both force-filter), `Unfilter Company` (reverses an AI filter) and `Company Regions` (manual region overrides, see below). Then `applyListChanges()` moves rows already in the sheet to match the current lists — before the dedup sets are loaded, so dedup sees where rows ended up.
2. Searches Gmail for alert emails from `CONFIG.MARK_EMAIL` within `CONFIG.LOOKBACK_DAYS`. Every email in the window goes to the AI on every run; dedup (step 5) stops repeats.
3. For each email, strips it down to job-relevant text via `prepareEmailForApi()` and sends it to Claude (`callClaudeForJobs()`) for classification.
4. Applies code-level overrides on top of the AI's classification, in this order: `Unfilter Company` (turns an AI `filter` back into `route`) → the two blocklists (`blocklistReason()`; force `filter`, so they beat Unfilter) → the Bournemouth/Poole/Christchurch check (`applyTownRegionRules()`: South West → Southern Home Counties) → `Company Regions` (only redirects jobs still at region `'Other'`).
5. Dedupes against existing sheet rows by exact link and by a normalized title/company/town key (see `normalizeJobKey()`). Dedup is permanent and has no exceptions: there is no resurfacing window and no retention purge (both removed in v19 — recoverable from git history at commit `c51aff2` if they're wanted back). Getting a job out of Filtered Out after a list change is `applyListChanges()`'s job, not dedup's.
6. Routes each job to its destination tab via `REGION_TO_TABS` (every region except `Other` goes to `New Leads`; `Other` keeps its own tab), or to `Needs Review` / `Filtered Out`. New Leads rows also get a Staff ID via `REGION_TO_STAFF_ID` and a blank Job Description. After each Indeed email, `startIndeedDescriptions()` starts an Apify run for that email's new ordinary Indeed leads (see "Job descriptions").
7. Rebuilds `New Leads` in full (see below); `Other`, `Needs Review` and `Filtered Out` are append-only.
8. Records today's date in Script Properties (`LAST_PROCESSING_SUCCESS_KEY`) — only reached if the run didn't throw. `runDailySend()` reads it.
9. `fillJobDescriptions()` fills column H for this run's new New Leads rows (see "Job descriptions"). It runs after the leads are saved and after step 8, inside `runDescriptionStep()`, so a description problem can never lose a lead or flag the run as failed.

**Staff ID column (New Leads column G):** `REGION_TO_STAFF_ID` is the old v17 region → consultant mapping, but it outputs the consultant's CRM Staff ID (from `STAFF_IDS`) instead of a name. `North West` maps to Craig only; v17 also sent it to Alison, but New Leads is one row per job. `Other` has no Staff ID because those jobs go to the `Other` tab. Rows written before v19 have a blank Staff ID: no region is stored per row, so it can't be derived after the fact.

**Header/column invariants:** New Leads uses `NEW_LEADS_HEADERS` (8 columns: `TAB_HEADERS` + `Staff ID` (G, `NL_STAFF_ID`) + `Job Description` (H, `NL_DESCRIPTION`)). Use those index constants rather than literal numbers. New Leads feeds the CRM import, so A–G stay exactly as v21 had them and new columns only ever go on the end (v22/v23 put the description in G and moved Staff ID — abandoned). `Other` still uses the 6-column `TAB_HEADERS` — don't add columns to `TAB_HEADERS`, or `ensureHeaders()` will insert a new header row into `Other`. Code all over the file assumes Date Found is column E (index 4) and Link is column F (index 5): dedup, sorting, date formatting, the fixed Link column width. Rows written before v24 read back with a blank Job Description; `applyListChanges()` appends 7-column rows to New Leads, which the rebuild pads.

**`REGION_TO_TABS` maps every region to its destination tab(s):** as of v18 every region except `Other` maps to the single `New Leads` tab. `ALL_TAB_NAMES` and `REBUILD_TABS` (currently just `New Leads`) are both derived from or tied to this map — extending routing to a second rebuilt tab means adding it to `REBUILD_TABS` too.

**Job links use a placeholder scheme to avoid truncation:** `prepareEmailForApi()` never sends real URLs to Claude — it replaces each job link with a short ID (`L1`, `L2`, ...) via `linkMap`, and Claude only ever echoes the ID back. `resolveJobLink()` maps the ID back to the real URL afterward. Any change to prompt construction or email parsing must preserve this indirection.

**Four override lists sit above the AI classification**, all maintained by hand as plain sheet tabs:
- `Company Blocklist` (single column) — force-filters a company regardless of AI output.
- `Job Title Blocklist` (single column) — same, for job titles. Only checked when the company isn't already blocked, so each job is counted once.
- `Unfilter Company` (single column) — if the AI filters a job from a listed company, it's turned back into a `route` and goes through normal routing with the region the AI gave (New Leads + Staff ID, or `Other` / `Needs Review` if the region is `Other` / missing). It only reverses the AI's own filter; the manual blocklists run afterwards and still win. This depends on the prompt asking for a region on filtered jobs too — don't remove that from `buildPrompt()`.
- All three single-column lists share `loadBlocklist()` and use `normalizeText()` exact matching: case and punctuation are ignored, but the whole value must match, so `Paralegal` does not block `Senior Paralegal`.
- `Company Regions` (Company | Region) — only fires when a job is already classified `action: 'route'` and `region: 'Other'`; redirects it to the locked-in region (and therefore that region's Staff ID) without touching the displayed `Town` value. Runs after the blocklist checks, so a blocklisted job never reaches this logic.

**List changes (`applyListChanges()`) apply the override lists to rows already in the sheet**, at the start of every `processJobAlerts()` run and via `applyListsNow()`. In order:
1. Blocklists: rows in New Leads, Other and Needs Review whose company/title is blocklisted move to Filtered Out with the blocklist reason.
2. Unfilter Company: Filtered Out rows for a listed company move out, unless their reason is a blocklist reason (`REASON_COMPANY_BLOCKLIST` / `REASON_TITLE_BLOCKLIST`) or the company/title is currently blocklisted. Filtered Out stores no region, so `lookupRegionsForRows()` asks the AI to place the towns (batches of `REGION_LOOKUP_BATCH_SIZE`). The rows then route as normal: New Leads with Staff ID, Other, or Needs Review (`REASON_UNFILTER_NO_REGION`). If the lookup fails they stay in Filtered Out and are retried next run.
3. Company Regions: Other rows for a listed company move to New Leads with that region's Staff ID. Runs last so it also catches rows step 2 just put in Other. New Leads rows are deliberately never re-assigned.

A moved row leaves its old tab, so each job lives in exactly one tab. Removing an entry from a list moves nothing back; it only affects future jobs. Moves go through `readRows()` / `takeRows()`, which assume a single header row (true for New Leads, Other, Needs Review and Filtered Out); `takeRows()` writes kept rows back through `safeCellText()` so descriptions stay text. New Leads rows are appended unsorted; the end-of-run rebuild sorts them. Rows moved into New Leads this way get no description.

**Job descriptions (New Leads column H) are downloaded, never written by the AI**, for the rows each `processJobAlerts()` run adds to New Leads from the emails, if found on or after `DESCRIPTION_CONFIG.START_DATE` (5 Oct 2026, `wantsDescription()`; earlier ones stay blank) — all within that one run (no backfill of older rows, no second step at 08:30, nothing carried between runs):
- **LinkedIn:** job ID from the link (`linkedInJobId()`, handles `/comm/` and slug URLs) → `https://www.linkedin.com/jobs-guest/jobs/api/jobPosting/<id>` via `UrlFetchApp.fetchAll` in batches of `LINKEDIN_BATCH_SIZE`. The description is the `show-more-less-html__markup` div, extracted with `divContents()` (counts nested divs) and `descriptionHtmlToText()`. No API key, Apify or AI. Claude's own web_fetch is blocked by LinkedIn; don't switch to it.
- **Indeed, ordinary jobs** (`jk` in the link, `indeedJobKey()`): Indeed blocks Apps Script (401/403), so they go to Apify's `misceres~indeed-scraper` as `viewjob?jk=` links (token in Script Property `APIFY_TOKEN`). Runs take 1–3 minutes, so `startIndeedDescriptions()` starts one run per Indeed email during the email loop (only that email's new leads, so filtered/duplicate jobs are never paid for), with Apify's own `timeout` set to the time left. At the end `collectIndeedRun()` waits for each run (`waitForFinish` polls of ≤45s), matches results to jobs by searching each result for the `jk`, and aborts any run still going at the deadline. Field names vary, hence `APIFY_DESCRIPTION_FIELDS`. Confirmed working on real jobs (test sheet, Oct 2026).
- **Indeed, sponsored jobs** (no `jk`): `DESCRIPTION_SPONSORED`, never sent to Apify — see "Working with this codebase".
- Anything not retrievable is `FETCH FAILED (reason)` — never a guess. Apify errors include Apify's own message (`apifyRequest()`). Text is capped at `MAX_CHARS` (45,000; a cell holds 50,000) and written via `writeDescriptions()` (one write to column H, only into blank cells, matched by Link) through `safeCellText()`, which prefixes `'` to text starting with `= + - @` so Sheets doesn't treat it as a formula. Read-back drops that apostrophe, so `rebuildNewLeadsTab()` and `takeRows()` re-apply it on every rewrite.

**Time limits:** Apps Script kills a run at 6 minutes. `processJobAlerts()` resets `runStartedAt`; `timeLeftMs()` counts down from `RUN_TIME_BUDGET_MS` (5 min). Email processing is unchanged from v21 and not time-limited; description work only uses what's left: no Apify run is started with under 90s left, LinkedIn batches stop with under 60s left, and Apify waiting stops 30s before the budget (the run is aborted, its leads FETCH FAILED). If the AI step itself ever approaches 6 minutes, the next fix is v22's idea of skipping already-processed emails (git history).

**`New Leads` rebuild (`rebuildNewLeadsTab()`) is a full read-clear-rewrite per run**, not an incremental append — this is what distinguishes it from `Other`'s always-append pattern (see `FLAT_TABS`). It reads back existing rows, merges in the run's new rows, dedupes by Link, sorts newest-first and rewrites the tab with a fresh header. On read-back, the header row is detected by comparing only the first 6 cells to `TAB_HEADERS`, so a pre-v19 header without Staff ID is still recognised and never carried forward as a job row. `sheet.clear()` wipes all formatting on every run, so manual formatting in New Leads does not survive. `formatNewLeadsLayout()` (also called after descriptions are written) keeps the tab neat: A–G auto-sized, Link and Job Description at fixed widths (`LINK_COLUMN_WIDTH_PX`, `DESCRIPTION_CONFIG.COLUMN_WIDTH_PX`) with clipped text, and every data row forced to single-line height (`setRowHeightsForced`, `DESCRIPTION_CONFIG.ROW_HEIGHT_PX`), because Sheets otherwise grows a row to show every line of a multi-line description regardless of the wrap setting. Don't auto-size column H. Because New Leads is never purged and descriptions make rows much bigger, this full rewrite gets slower as the tab grows — worth revisiting (archive/purge) if runs start nearing the time budget.

**`migrateConsultantTabsToNewLeads()` is a one-off migration** (v17's 5 consultant tabs → v18's single `New Leads`): it pulls every job row out of `Craig`/`Alison`/`Tom`/`Josh`/`Ray`, dedupes by `Link`, pads each row with a blank Staff ID and Job Description, and feeds the result through `rebuildNewLeadsTab()`. It leaves the old tabs in place — they're deleted manually once `New Leads` looks right, not by the script.

**Daily schedule (bottom of the file):** two time-based triggers, created by `createDailyTriggers()` in `DAILY_SEND_CONFIG.TIME_ZONE` (Europe/London): `processJobAlerts()` at ~07:30 and `runDailySend()` at ~08:30. `runDailySend()` is unchanged from v21 and does no description work. It emails the workbook as an `.xlsx` attachment plus a link to the live Google Sheet to `DAILY_SEND_CONFIG.RECIPIENT_EMAILS`. Each send also calls `addViewers()` for the recipients so the link opens for them (it never downgrades existing editors); if sharing fails, the failure is logged and the email is still sent. `nearMinute()` triggers fire within ±15 minutes, so the runs are always ≥30 minutes apart; Apps Script caps a run at 6 minutes, so the send can't overtake processing. If that morning's processing didn't record success (see step 8 above), the email still goes out, flagged "(processing error)" with a warning in the body. `createDailyTriggers()` / `removeDailyTriggers()` first delete every trigger whose handler is in `SCHEDULE_HANDLERS` — including the pre-v20 `dailyRunAndSend` — so they're safe to re-run and clean up old schedules. Copying the Sheet copies the script but not its triggers, so a copy needs `createDailyTriggers()` run again.

**Claude API usage:** `callClaude()` is the single HTTP wrapper: it calls `CONFIG.CLAUDE_API_URL` directly via `UrlFetchApp` (no SDK) and returns a parsed JSON array, or `null` on any failure. `callClaudeForJobs()` (email extraction) and `lookupRegionsForRows()` (placing existing rows in a region) both use it, and both prompts embed the shared `REGION_RULES` block, so region rules live in one place. It's authenticated with `CLAUDE_API_KEY` from Script Properties (Project Settings → Script Properties in the Apps Script editor — never hardcoded). Model is `CONFIG.CLAUDE_MODEL`; the prompt in `buildPrompt()` (filtering rules) plus `REGION_RULES` (region assignment, including the East Anglia/Peterborough and Bournemouth/Poole/Christchurch exceptions) is the source of truth for classification rules — region logic changes should generally go there rather than in post-processing code, unless they're deterministic overrides like the override lists. The Bournemouth/Poole/Christchurch rule is the one region rule that's in both places: `REGION_RULES`, plus `SOUTHERN_HOME_COUNTIES_TOWNS` / `applyTownRegionRules()` in code as a guarantee — keep them in sync.
