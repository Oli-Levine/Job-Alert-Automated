# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A single Google Apps Script file (`Code.gs`) that automates job-alert triage for BCL Legal. It is bound to a Google Sheet, reads LinkedIn/Indeed job-alert emails from Gmail, classifies each listing with the Claude API, downloads each lead's full job description, and writes results into a `New Leads` tab that is imported directly into the company CRM. There is no package manager, build step, linter, or test runner — this is plain Apps Script (V8 runtime) deployed by pasting the file's contents into the Apps Script editor (which names the file `Code.gs` by default) bound to the Google Sheet.

## Working with this codebase

- There is only one source file, `Code.gs`. The filename is stable across versions — do NOT rename it per version (an earlier convention renamed the file itself, e.g. `V17` → `V18`; that's retired, since it fought git's own history instead of using it). Version identity lives in exactly two places: the header comment's version number (bump it on a meaningful change) and git history/log (use `git log`, `git diff`, or `git show <commit>:Code.gs` to inspect or recover a prior version).
- The file's top-of-file comment block is a running changelog ("CHANGES FROM v18", "CHANGES FROM v17 (carried forward)", ...), keeping the two most recent entries and dropping older ones. When making a meaningful change, bump the version number in the header comment and add a new entry describing what changed and why — this is the project's in-file changelog; git history is the source of truth for anything older than what it keeps.
- There's no automated test suite. Verification happens via the diagnostic/dry-run functions defined in the file itself, run manually from the Apps Script editor against the live Gmail/Sheet data:
  - `testParseLatestEmail()` — dry run: parses the latest matching email and logs what Claude would classify (the Staff ID a routed job would get, and the region a filtered job would use if unfiltered), without writing anything. It does not apply the blocklists, Unfilter Company, Company Regions or the Bournemouth/Poole/Christchurch code check.
  - `debugIndeedLinks()` — logs raw vs. detected Indeed job links, for diagnosing link-extraction regressions.
  - `debugListSheetNames()` — logs actual sheet tab names vs. expected working tab names (catches naming/whitespace mismatches).
  - `listAllTriggers()` — lists what time-based triggers are currently installed on this sheet's script.
  - `runDailySend()` — can be run by hand to send the workbook email immediately.
  - `applyListsNow()` — re-applies the override lists to rows already in the sheet straight away (see "List changes" below), without fetching new emails.
  - `fillJobDescriptionsNow()` — fills job descriptions for leads inside the description window straight away, waiting for Apify. `debugIndeedDescriptions()` — dry run of the Apify (Indeed) route on up to three leads; logs result field names and descriptions, writes nothing. `debugSponsoredIndeed()` — experiment for sponsored Indeed jobs (ad links with no job ID; Indeed refuses them with a 403, and Apify's scraper rejects them too). On up to three sponsored New Leads rows it compares three Indeed searches via Apify (company + town, title + town, title + company anywhere) and logs, per lead, whether each finds an exact or loose company + title match. Writes nothing.
- `resetAllJobData()` is a destructive utility for the live spreadsheet — don't suggest running it casually. `migrateConsultantTabsToNewLeads()` is a one-off migration (see below) meant to be run once, not on a schedule.
- Because the sheet feeds a CRM import, the New Leads column layout is effectively an external contract — adding, removing or reordering its columns affects the import, so treat it as a user decision, not a refactor.

## Architecture

**Entry point:** `processJobAlerts()` is the main daily job. It:
0. Converts New Leads to the current column layout if needed (`ensureNewLeadsLayout()`) — before anything appends to it — then collects any finished Apify runs.
1. Loads reference/override sheets (`loadOverrideLists()`): `Company Blocklist`, `Job Title Blocklist` (both force-filter), `Unfilter Company` (reverses an AI filter) and `Company Regions` (manual region overrides, see below). Then `applyListChanges()` moves rows already in the sheet to match the current lists — before the dedup sets are loaded, so dedup sees where rows ended up.
2. Searches Gmail for alert emails from `CONFIG.MARK_EMAIL` within `CONFIG.LOOKBACK_DAYS`, skipping any already processed (`PROCESSED_MESSAGES_KEY` in Script Properties). An email is only marked processed once all its jobs are handled; one whose AI call fails, or that's left because the run passed `EMAIL_TIME_BUDGET_MS`, is picked up next run.
3. For each email, strips it down to job-relevant text via `prepareEmailForApi()` and sends it to Claude (`callClaudeForJobs()`) for classification.
4. Applies code-level overrides on top of the AI's classification, in this order: `Unfilter Company` (turns an AI `filter` back into `route`) → the two blocklists (`blocklistReason()`; force `filter`, so they beat Unfilter) → the Bournemouth/Poole/Christchurch check (`applyTownRegionRules()`: South West → Southern Home Counties) → `Company Regions` (only redirects jobs still at region `'Other'`).
5. Dedupes against existing sheet rows by exact link and by a normalized title/company/town key (see `normalizeJobKey()`). Dedup is permanent and has no exceptions: there is no resurfacing window and no retention purge (both removed in v19 — recoverable from git history at commit `c51aff2` if they're wanted back). Getting a job out of Filtered Out after a list change is `applyListChanges()`'s job, not dedup's.
6. Routes each job to its destination tab via `REGION_TO_TABS` (every region except `Other` goes to `New Leads`; `Other` keeps its own tab), or to `Needs Review` / `Filtered Out`. New Leads rows also get a Staff ID via `REGION_TO_STAFF_ID`.
7. Rebuilds `New Leads` in full (see below); `Other`, `Needs Review` and `Filtered Out` are append-only. Then `fillJobDescriptions()` (see "Job descriptions" below).
8. Records today's date in Script Properties (`LAST_PROCESSING_SUCCESS_KEY`) — only reached if the run didn't throw. `runDailySend()` reads it.

**Staff ID column (New Leads column H):** `REGION_TO_STAFF_ID` is the old v17 region → consultant mapping, but it outputs the consultant's CRM Staff ID (from `STAFF_IDS`) instead of a name. `North West` maps to Craig only; v17 also sent it to Alison, but New Leads is one row per job. `Other` has no Staff ID because those jobs go to the `Other` tab. Rows written before v19 have a blank Staff ID: no region is stored per row, so it can't be derived after the fact.

**Header/column invariants:** New Leads uses `NEW_LEADS_HEADERS` (8 columns: `TAB_HEADERS` + `Job Description` (G, `NL_DESCRIPTION`) + `Staff ID` (H, `NL_STAFF_ID`)). Use those index constants rather than literal numbers. `Other` still uses the 6-column `TAB_HEADERS` — don't add columns to `TAB_HEADERS`, or `ensureHeaders()` will insert a new header row into `Other`. Code all over the file assumes Date Found is column E (index 4) and Link is column F (index 5): dedup, sorting, date formatting, the fixed Link column width — so new New Leads columns go after F. v19–v21 had Staff ID in G; `rebuildNewLeadsTab()` converts that layout on read-back (detected from the header), and `ensureNewLeadsLayout()` triggers it before anything appends rows.

**`REGION_TO_TABS` maps every region to its destination tab(s):** as of v18 every region except `Other` maps to the single `New Leads` tab. `ALL_TAB_NAMES` and `REBUILD_TABS` (currently just `New Leads`) are both derived from or tied to this map — extending routing to a second rebuilt tab means adding it to `REBUILD_TABS` too.

**Job links use a placeholder scheme to avoid truncation:** `prepareEmailForApi()` never sends real URLs to Claude — it replaces each job link with a short ID (`L1`, `L2`, ...) via `linkMap`, and Claude only ever echoes the ID back. `resolveJobLink()` maps the ID back to the real URL afterward. Any change to prompt construction or email parsing must preserve this indirection.

**Four override lists sit above the AI classification**, all maintained by hand as plain sheet tabs:
- `Company Blocklist` (single column) — force-filters a company regardless of AI output.
- `Job Title Blocklist` (single column) — same, for job titles. Only checked when the company isn't already blocked, so each job is counted once.
- `Unfilter Company` (single column) — if the AI filters a job from a listed company, it's turned back into a `route` and goes through normal routing with the region the AI gave (New Leads + Staff ID, or `Other` / `Needs Review` if the region is `Other` / missing). It only reverses the AI's own filter; the manual blocklists run afterwards and still win. This depends on the prompt asking for a region on filtered jobs too — don't remove that from `buildPrompt()`.
- All three single-column lists share `loadBlocklist()` and use `normalizeText()` exact matching: case and punctuation are ignored, but the whole value must match, so `Paralegal` does not block `Senior Paralegal`.
- `Company Regions` (Company | Region) — only fires when a job is already classified `action: 'route'` and `region: 'Other'`; redirects it to the locked-in region (and therefore that region's Staff ID) without touching the displayed `Town` value. Runs after the blocklist checks, so a blocklisted job never reaches this logic.

**List changes (`applyListChanges()`) apply the override lists to rows already in the sheet**, at the start of every `processJobAlerts()` run and via `applyListsNow()`. In order:
1. Blocklists: rows in New Leads, Other and Needs Review whose company/title is blocklisted move to Filtered Out with the blocklist reason.
2. Unfilter Company: Filtered Out rows for a listed company move out, unless their reason is a blocklist reason (`REASON_COMPANY_BLOCKLIST` / `REASON_TITLE_BLOCKLIST`) or the company/title is currently blocklisted. Filtered Out stores no region, so `lookupRegionsForRows()` asks the AI to place the towns (batches of `REGION_LOOKUP_BATCH_SIZE`). The rows then route as normal: New Leads with Staff ID, Other, or Needs Review (`REASON_UNFILTER_NO_REGION`). If the lookup fails they stay in Filtered Out and are retried next run.
3. Company Regions: Other rows for a listed company move to New Leads with that region's Staff ID. Runs last so it also catches rows step 2 just put in Other. New Leads rows are deliberately never re-assigned.

A moved row leaves its old tab, so each job lives in exactly one tab. Removing an entry from a list moves nothing back; it only affects future jobs. Moves go through `readRows()` / `takeRows()`, which assume a single header row (true for New Leads, Other, Needs Review and Filtered Out). New Leads rows are appended unsorted; the end-of-run rebuild sorts them.

**Job descriptions (New Leads column G) are downloaded, never written by the AI.** Only leads inside the window (`inDescriptionWindow()`: found within `DESCRIPTION_CONFIG.FILL_DAYS` = 7 days and not before `START_DATE` = 3 Oct 2026) are ever fetched. `fillJobDescriptions(sheet, retryFailed)` fills blank cells in the window (plus `FETCH FAILED` ones when `retryFailed`, which only the 07:30 run passes, and `PENDING` ones whose Apify run is no longer tracked):
- **LinkedIn:** job ID from the link (`linkedInJobId()`, handles `/comm/` and slug URLs) → `https://www.linkedin.com/jobs-guest/jobs/api/jobPosting/<id>` via `UrlFetchApp.fetchAll` in batches of `LINKEDIN_BATCH_SIZE`. The description is the `show-more-less-html__markup` div, extracted with `divContents()` (counts nested divs) and `descriptionHtmlToText()`. Claude's own web_fetch is blocked by LinkedIn; don't switch to it.
- **Indeed:** blocks Apps Script (401/403) and its alert emails carry no description, so all the run's Indeed jobs (by `jk`, `indeedJobKey()`) go to one Apify run of `misceres~indeed-scraper` (`startApifyRun()`, token in Script Property `APIFY_TOKEN`). Runs take 1–3 minutes, so they're started without waiting and remembered in Script Properties (`APIFY_RUNS_KEY`); cells say `DESCRIPTION_PENDING`. `collectApifyRuns(sheet, maxWaitMs)` writes finished runs' results into the PENDING rows, matching each result to a job by searching it for the `jk`. Field names vary, hence `APIFY_DESCRIPTION_FIELDS`. Sponsored Indeed links (`pagead/clk` ad-tracking redirects) carry no `jk`: `resolveIndeedJobKeys()` opens each with `followRedirects: false` and reads the `Location` header (up to 3 hops, never downloading the blocked job page) to get it, then rewrites the row's Link to the clean `viewjob?jk=` URL so the Apify result can be matched back. A redirect to the employer's own site, or a refused request, becomes `FETCH FAILED` with that reason. A run unfinished after `APIFY_STALE_HOURS` is given up on. This route was built but not confirmed on a real run before v22 — `debugIndeedDescriptions()` checks it.
- Anything not retrievable is `FETCH FAILED (reason)` — never a guess. For Apify errors the reason includes Apify's own error message (`apifyRequest()`), and each collected run logs its status, result count and the field names of its first result — check the execution log first when Indeed descriptions fail. Text is capped at `MAX_CHARS` (45,000; a cell holds 50,000) and written through `safeCellText()`, which prefixes `'` to text starting with `= + - @` so Sheets doesn't treat it as a formula. Read-back drops that apostrophe, so `rebuildNewLeadsTab()` re-applies it on every rewrite.
- Description steps run inside `runDescriptionStep()` (try/catch): a failure there is logged and retried next run, never allowed to fail `processJobAlerts()` or block the email.

**Time limits:** Apps Script kills a run at 6 minutes. Each entry point resets `runStartedAt`; `timeLeftMs()` counts down from `RUN_TIME_BUDGET_MS` (5 min). New emails stop being started past `EMAIL_TIME_BUDGET_MS` (3.5 min), LinkedIn batches stop with under 60s left, and Apify polling respects both a caller deadline and the budget. Work left over is picked up by the next run. That's also why Indeed descriptions are split across the two daily runs: the 07:30 run starts Apify and the 08:30 `runDailySend()` collects.

**`New Leads` rebuild (`rebuildNewLeadsTab()`) is a full read-clear-rewrite per run**, not an incremental append — this is what distinguishes it from `Other`'s always-append pattern (see `FLAT_TABS`). It reads back existing rows, merges in the run's new rows, dedupes by Link, sorts newest-first and rewrites the tab with a fresh header. On read-back, the header row is detected by comparing only the first 6 cells to `TAB_HEADERS`, so a pre-v19 header without Staff ID is still recognised and never carried forward as a job row. `sheet.clear()` wipes all formatting on every run, so manual formatting in New Leads does not survive. The description column gets a fixed width (`DESCRIPTION_COLUMN_WIDTH_PX`) and clipped text instead of auto-sizing. Data rows are also forced to single-line height (`setRowHeightsForced`, `NEW_LEADS_ROW_HEIGHT_PX`), because Sheets otherwise grows a row to show every line of a multi-line description regardless of the wrap setting. Because New Leads is never purged and descriptions make rows much bigger, this full rewrite gets slower as the tab grows — worth revisiting (archive/purge) if runs start nearing the time budget.

**`migrateConsultantTabsToNewLeads()` is a one-off migration** (v17's 5 consultant tabs → v18's single `New Leads`): it pulls every job row out of `Craig`/`Alison`/`Tom`/`Josh`/`Ray`, dedupes by `Link`, pads each row with a blank Job Description and Staff ID, and feeds the result through `rebuildNewLeadsTab()`. It leaves the old tabs in place — they're deleted manually once `New Leads` looks right, not by the script.

**Daily schedule (bottom of the file):** two time-based triggers, created by `createDailyTriggers()` in `DAILY_SEND_CONFIG.TIME_ZONE` (Europe/London): `processJobAlerts()` at ~07:30 and `runDailySend()` at ~08:30. Before exporting, `runDailySend()` fills any blank descriptions, collects the Indeed results from Apify (waiting up to `SEND_WAIT_SECONDS`, leaving ~90s of budget for the send), calls `SpreadsheetApp.flush()`, and adds `descriptionStatusLine()` to the email body. It then emails the workbook as an `.xlsx` attachment plus a link to the live Google Sheet to `DAILY_SEND_CONFIG.RECIPIENT_EMAILS`. Each send also calls `addViewers()` for the recipients so the link opens for them (it never downgrades existing editors); if sharing fails, the failure is logged and the email is still sent. `nearMinute()` triggers fire within ±15 minutes, so the runs are always ≥30 minutes apart; Apps Script caps a run at 6 minutes, so the send can't overtake processing. If that morning's processing didn't record success (see step 8 above), the email still goes out, flagged "(processing error)" with a warning in the body. `createDailyTriggers()` / `removeDailyTriggers()` first delete every trigger whose handler is in `SCHEDULE_HANDLERS` — including the pre-v20 `dailyRunAndSend` — so they're safe to re-run and clean up old schedules. Copying the Sheet copies the script but not its triggers, so a copy needs `createDailyTriggers()` run again.

**Claude API usage:** `callClaude()` is the single HTTP wrapper: it calls `CONFIG.CLAUDE_API_URL` directly via `UrlFetchApp` (no SDK) and returns a parsed JSON array, or `null` on any failure. `callClaudeForJobs()` (email extraction) and `lookupRegionsForRows()` (placing existing rows in a region) both use it, and both prompts embed the shared `REGION_RULES` block, so region rules live in one place. It's authenticated with `CLAUDE_API_KEY` from Script Properties (Project Settings → Script Properties in the Apps Script editor — never hardcoded). Model is `CONFIG.CLAUDE_MODEL`; the prompt in `buildPrompt()` (filtering rules) plus `REGION_RULES` (region assignment, including the East Anglia/Peterborough and Bournemouth/Poole/Christchurch exceptions) is the source of truth for classification rules — region logic changes should generally go there rather than in post-processing code, unless they're deterministic overrides like the override lists. The Bournemouth/Poole/Christchurch rule is the one region rule that's in both places: `REGION_RULES`, plus `SOUTHERN_HOME_COUNTIES_TOWNS` / `applyTownRegionRules()` in code as a guarantee — keep them in sync.
